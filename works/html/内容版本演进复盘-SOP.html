内容版本演进复盘 SOP

2026-07-17 说明：本 HTML 为历史展示版，部分示例仍保留旧版本号和“精选过程稿”口径。AI 调用复盘流程时，以同目录 内容版本演进复盘-SOP.md 的最新规则为准：0.0 至【终稿】过程版本完整保留，不再按旧口径删除过程稿。

一句话定位：把每一份教研产出（大纲、单集教研、交互题等）从初稿到定稿的“修改判断”，用 git + Cursor 系统化地榨出可复用的教研规律，沉淀成团队资产。

首次落地案例：E5 大禹治水交互题（见 SKU1-史前与夏商周/交互题/复盘/E5大禹治水-版本演进复盘.md）

适用范围：大纲、单集教研、交互题等所有需要多轮迭代的内容产出。下文以 E5 交互题为例，但流程对所有内容类型同样适用。

一、这份 SOP 解决什么问题

我们每一份内容产出（大纲、单集教研、交互题等）都会经历“AI 基于 skill 生成 → 人工微调 → 组内讨论 → 专家审核”多轮迭代，每次修改背后都有一次“教研判断”。如果这些判断只留在脑子里，下一份内容还得重新踩坑。

这份 SOP 把这些藏在版本差异里的判断系统性地挖出来，沉淀成：

  • 一份每个产出的复盘 md（教研判断档案，可作为新人培训材料）
  • 一批可加进对应规范文档的规律条目（❌反例 → ✅正例 格式）——交互题进《AI 出题手册》、单集教研进《分集资料规则补充》、大纲进对应规范文档，依此类推
  • 一套可复用的工作习惯（commit 规范、tag 规范、文件归位规范）

关于“对应规范文档”：每种内容类型有自己对应的规范文档——交互题对应《AI 出题手册》，单集教研对应《分集资料规则补充》，大纲目前在沉淀对应规范。复盘提炼出的规律，写入哪个文档由内容类型决定，不是统一写入“出题手册”。

三、5 条核心原则（不变量）

  1. commit 节奏 = 判断节奏——有判断才 commit，没有判断的微调可以攒一起
  2. 「评估」和「精细对比」必须分两次 prompt——让 AI 一步到位会被回摆动作淹没
  3. 删之前必先打 tag——0 成本买“永远反悔的权利”
  4. 复盘 md 是终极交付物——比规律本身更值钱的是“判断链路”
  5. 整理只动工作区，不动 git 历史——git 历史是只增不减的时间机器

四、流程详解（按时间线）

阶段 1：日常阶段 —— commit 规范

目的：让 git 历史里的每个 commit 都对应一次真正的“教研判断”，为后续复盘提供清晰的版本节点。

1.1 什么时候 commit

下方示例以交互题为例，其他内容类型（大纲、单集教研等）同理——把“集名”换成对应内容标识即可。

修改类型 要不要 commit commit message 示例
AI 基于 skill 生成一版 ✅ 必 E5 交互题 v2.0｜AI 基于 skill 重生成
改错字 / 调措辞 ❌ 攒一起 ——
调整结构 / 改考查点 / 改章节 ✅ 必 E5 交互题 v2.1｜人工调整：Q3 题型改为连线
组内讨论后修改 ✅ 必 E7 单集教研 v3.0｜组内讨论后：第二幕推翻重做
专家审核后修改 ✅ 必 E5 交互题 v4.0｜专家审核后：Q1 选项简化

1.2 commit message 格式

{产出标识} v{版本号}｜{修改来源}：{修改内容简述}
  • 产出标识：能让人一眼看出是哪份内容的哪个类型，如 E5 交互题 / E7 单集教研 / 秦汉时期 大纲
  • 修改来源统一用这几个词：AI 基于 skill 生成 / 人工调整 / 组内讨论后 / 专家审核后 / 品控反馈后
  • 修改内容写关键判断，比如 “Q3 题型改为连线”、“第二幕推翻重做”，不要写 “改了一些字”

1.3 文件命名规范

{产出标识}-{版本号}.md

各类型示例：

内容类型 命名示例
大纲 秦汉时期-大纲2.0.md
单集教研 E7武帝大一统-分集资料2.0.md
交互题 E5 大禹治水-交互题2.0.md

同时存在多版时，建议用文件名标版本号；不必为了“管理整洁”过早删除中间版本——定稿后会统一整理。

阶段 2：定稿一刻 —— 打 tag

目的：在做任何“清理动作”前，给 git 历史打一个时间锚点，相当于把“完整版本档案”那一刻拍照存档。

2.1 命令

git tag {产出标识}-完整版本档案-{YYYYMMDD}

各类型示例：

git tag E5-交互题-完整版本档案-20260601
git tag E7-单集教研-完整版本档案-20260601
git tag 秦汉时期-大纲-完整版本档案-20260601

2.2 把 tag 推到远端（让团队能用）

git push origin {产出标识}-完整版本档案-{YYYYMMDD}

为什么必须做：后面要删冗余过程稿。万一删错、或者某天想穿越回完整态查证某个判断，有 tag 就能 git checkout {tag名} 一键复活，没有就要靠 commit hash 翻历史。

0 成本的保险，没有理由不做。

阶段 3：复盘阶段 —— 三段式 AI 对话

核心原则：「评估」与「精细对比」必须分开。一次 prompt 试图同时做两件事，AI 会被淹没在回摆动作里。

Step 1：让 AI 评估「判断密度」

目的：从全部历史版本里，挑出真正值得做精细对比的 3-4 版。

prompt 模板（直接复制使用，替换 {产出标识} 和 {相关路径}）：

我想对比 {产出标识，如 "E5 大禹治水交互题" / "E7 武帝大一统单集教研"} 的全部历史版本，沉淀教研规律。

请你：
1. 用 git log --all --oneline -- "{相关文件或文件夹路径}" 找出所有相关 commit
2. 用 git show <commit>:<filepath> 把每个版本的内容取出来
3. 按"判断密度"评估每一版——判断密度 = 该版相比上一版新增的、可追溯的、带理由的设计判断数量
4. 推荐保留 3-4 版作为后续精细对比的核心版本，并说明每版的不可替代性

输出格式：
- 版本时间线表格（版本号 / commit / 日期 / 文件位置 / 行数 / 修改性质）
- 判断密度评分表（每版按维度打分）
- 推荐保留的 N 版及理由

注意事项： - 不要让 AI 直接做精细对比——这一步只让它评估“哪几版值得对比” - AI 的判断会基于 commit message——所以阶段 1 的 commit 规范有多用心，这一步质量就有多高

Step 2：人工敲定（不是 AI 决定）

目的：AI 的评估是“算出来的”，但“该保留哪几版”是教研判断，必须人来拍板。

操作：看完 AI 输出的评估表后，直接回复你最终决定保留的版本号，例如：

就保留 v0、v3.0、v4.0、终稿 这 4 版。

Step 3：让 AI 基于敲定版做「精细对比」

目的：每处修改的教研判断，逐条挖出来。

prompt 模板：

只针对我敲定的 {版本列表} 这 N 版，重新做精细对比。

要求：
1. 按"题号 → 跃迁次数"组织（如 v0 → v3.0 是第 1 次跃迁，v3.0 → v4.0 是第 2 次……）
2. 每次跃迁里的每处修改，用以下三段格式分析：
   - 修改：从 X 改为 Y
   - 教研意图：为什么改（要能解释清楚教学价值的提升）
   - 适用场景：这条判断未来在什么类型的考查点上可以复用

不要再分析未敲定的版本，专注于这 N 版的演进。

Step 4：让 AI 沉淀「可复用规律」

目的：把“修改判断”提炼成可以加进对应规范文档的、与现有原则不重复的新条目。

注意：写入哪份规范文档由内容类型决定——交互题进《AI 出题手册》、单集教研进《分集资料规则补充》、大纲进对应规范，不要统一写进“出题手册”。

prompt 模板：

基于刚才推出的修改规律，整理成 3-5 条可以加进对应规范文档的具体条目。

不同内容类型对应的规范文档示例：
- 交互题 → @02-交互题/上下五千年交互-AI出题手册.md
- 单集教研 → @SKU{N}-{时期}/单集教研内容/{对应规则补充}.md
- 大纲 → 对应大纲规范文档（沉淀中）

要求：
1. 先快速读一下现有规范文档，确保新条目与已有原则不重复
2. 每条用"❌ 反例 → ✅ 正例"格式
3. 反例和正例都用本次复盘中真实出现过的内容，不要编造
4. 每条标注"建议放在第几章 / 紧跟原则几之后"
5. 先在对话框里给我看候选，等我确认后再写入文档

注意事项： - 强烈建议加“先给我看候选、等我确认后再改文档”——AI 直接动规范文档容易把不该加的也加进去 - 规范文档新增条目应同步在 commit message 写明：“{规范文档名} 新增原则 N：{标题}，来源 {产出标识} 复盘”

阶段 4：收口阶段 —— 沉淀复盘 md + 更新对应规范文档

目的：把整个复盘过程的产出固化为可被反复引用的资产。

4.1 让 AI 生成「复盘 md」

prompt 模板：

帮我把以上整个复盘对话整理成一份 md 文档，放在该内容产出对应的"复盘"目录下，
命名为 "{产出标识}-版本演进复盘.md"。如果"复盘"目录不存在，先新建一个。

具体路径示例：
- 交互题 → SKU{N}-{时期}/交互题/复盘/
- 单集教研 → SKU{N}-{时期}/单集教研内容/复盘/
- 大纲 → SKU{N}-{时期}/大纲策划/复盘/

要求保留：
1. 版本时间线表格
2. 判断密度评估表
3. 敲定的 N 版精细对比（按章节/题号 + 跃迁次数组织）
4. 提炼的 N 条规律（❌反例 → ✅正例 格式）
5. 末尾附一节"后续可复用清单"——简述这些规律在什么场景下复用

不要省略关键判断的细节，这份文档会作为团队培训材料。

4.2 更新对应规范文档

确认 AI 给出的条目无误后：

确认 {条目列表} 这 N 条加入对应规范文档，按你建议的位置插入。
插入后再读一遍文档，确保新旧条目衔接自然、没有概念冲突。

4.3 commit 收口

git add .
git commit -m "{产出标识} 复盘归档：新增复盘 md，{规范文档名}新增原则 N-M"

阶段 5：整理阶段 —— 文件归位

目的：保持工作区清晰，但精选过程稿留作“未来可直接 @ 的素材”。

5.1 归位规则

文件类型 归位文件夹 说明
终稿 对应内容类型的“终稿”目录 最终版本
精选过程稿（敲定要保留的） 对应内容类型的“过程稿”目录 后续培训 / 参考会直接 @
复盘 md 对应内容类型的“复盘”目录（如不存在则新建） 与原始过程稿分离，便于复盘和培训独立查阅
辅助文档（如交互题的考查点、教研内容的素材清单等） 对应内容类型的“过程稿”目录 已是惯例
其他过程稿 删除 git 历史里还在，需要时用 git show 取

关于“复盘”目录的位置（当前设想，待团队讨论）：在每个内容类型的大文件夹下新建一个“复盘”子目录，把对应类型的复盘 md 都放进去。这样做的好处是把“判断档案”与原始过程稿分开——团队复盘 / 培训时去“复盘/”目录就够，不会被中间版本干扰。

具体路径示例： - 交互题：SKU{N}-{时期}/交互题/{终稿|过程稿|复盘}/ - 单集教研：SKU{N}-{时期}/单集教研内容/{过程稿|复盘}/（终稿可能直接在内容根目录） - 大纲：SKU{N}-{时期}/大纲策划/{过程稿|复盘}/

具体目录结构按本项目实际惯例走，定稿后再统一。

5.2 操作步骤（以交互题为例，其他类型按实际路径调整）

# Step 1：把终稿移到终稿文件夹（如果还在过程稿里）
mv "{当前路径}/{产出标识}-定稿{日期}.md" \
   "{对应终稿目录}/"

# Step 2：删除非精选的过程稿
rm "{对应过程稿目录}/{产出标识}-{要删的版本号}.md"

# Step 3：确认精选过程稿和复盘 md 都在 过程稿目录 下
ls "{对应过程稿目录}/" | grep {产出标识}

# Step 4：commit 整理动作
git add .
git commit -m "{产出标识} 定稿后整理：终稿移入终稿目录，保留精选过程稿 {v1/v3} 和复盘 md，删除冗余过程稿 {v2/v4/v5}。完整历史见 tag {产出标识}-完整版本档案-{日期}"

# Step 5：推送
git push

5.3 检查清单（整理完做一遍）

  • [ ] 终稿在对应“终稿”目录下
  • [ ] 精选过程稿（2-3 版）在对应“过程稿”目录下
  • [ ] 复盘 md 在对应“复盘”目录下，命名为 {产出标识}-版本演进复盘.md
  • [ ] 辅助文档（考查点、素材清单等）保留在对应“过程稿”目录下
  • [ ] 其他冗余过程稿已删除
  • [ ] tag 已打且已 push
  • [ ] 整理动作已 commit 且 push
  • [ ] 对应规范文档新增条目已 commit

五、常用 Prompt 模板速查

复制即用，记得替换 {占位符}。

P1｜评估判断密度

我想对比 {产出标识} 的全部历史版本。
请你用 git log 找出全部相关 commit，按"判断密度"评估每版，
推荐保留 3-4 版作为后续精细对比的核心版本，说明每版不可替代性。

P2｜精细对比

只针对 {版本列表} 这 N 版，按"章节/题号 → 跃迁次数"组织，
每处修改用"修改 → 教研意图 → 适用场景"三段格式分析。

P3｜沉淀规律

把上述规律整理成 3-5 条可加进对应规范文档的条目。
每条用"❌反例 → ✅正例"格式，反例正例来自本次复盘真实出现过的内容。
先给我看候选，等我确认后再写入文档。

P4｜生成复盘 md

把以上对话整理成 {产出标识}-版本演进复盘.md，放在对应"复盘"目录下（不存在则新建）。
保留：版本时间线、判断密度评估、精细对比、规律条目、后续可复用清单。

P5｜穿越回完整态查证某个判断（事后任何时候）

请 git checkout 到 tag {产出标识}-完整版本档案-{日期}，
取出 {版本号} 的内容，告诉我 {具体问题}。
查完恢复到 main 分支。

六、常用 Git 命令速查

# 查看某文件夹下所有 commit
git log --all --oneline -- "{文件夹路径}"

# 查看某 commit 改了哪些文件
git show --stat {commit_hash}

# 取出历史某版本的文件内容
git show {commit_hash}:"{文件路径}"

# 打 tag
git tag {tag_名}
git push origin {tag_名}

# 列出所有 tag
git tag

# 穿越回某 tag 那一刻（看完记得回 main）
git checkout {tag_名}
git checkout main

# 找一个被删的文件最后存在于哪个 commit
git log --all --diff-filter=D -- "{文件路径}"

七、常见坑与对策

坑 表现 对策
commit 太碎 每改个字都 commit，复盘时 AI 被淹没 按“判断节奏”commit，不是“键盘节奏”
commit message 太简 “更新文件” “改了下” 强制用统一格式：{产出标识} v{号}｜{来源}：{内容}
一次 prompt 让 AI 做完所有事 输出又长又散，关键判断被回摆动作稀释 严格分 3 段：评估 → 对比 → 沉淀
删之前没打 tag 删完后悔，要翻 commit hash 才能找回 形成肌肉记忆——“删之前先 tag”
AI 自动改规范文档 加进去不合适的条目 prompt 里加“先给我看候选，确认后再改”
复盘 md 写得太摘要 失去“判断链路”的细节，培训价值降低 prompt 里强调“不要省略关键判断细节”
整理时用 git show > file.md 写回工作区 文件断开 commit 历史链 走“工作区中本来留下来的留下、本来没有的不补”——靠 git 历史和 tag 兜底

八、把这份 SOP 用起来的第一步

下次要交付任何内容产出（如某 SKU 大纲、某集单集教研、某集交互题等）的定稿时：

  1. 先在对话框里贴这份 SOP 给 Cursor，让它对照流程帮你跑
  2. 跑完后对照“检查清单”过一遍
  3. 跑顺一次后，把这份 SOP 同步给团队

跑通 2-3 个产出后，每次复盘时间会压缩到 30 分钟内，但沉淀下来的“教研判断档案”会越来越厚，最终会比任何外部 SOP 都贴合我们项目自己的成长曲线。
